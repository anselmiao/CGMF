# Run #317: discrete-level data provenance audit

**Branch:** `qi/fix-discrete-start-index`  
**Scope:** I-136 / ZAID 53136; origin of the runtime `discreteLevels.dat` level scheme  
**Purpose:** distinguish runtime filtering from offline RIPL-to-CGMF preparation  
**Status:** source-path facts verified; exact historical artifact-generation invocation remains BLOCKED

## Executive finding

The current source separates two stages:

1. **Runtime load:** `readDiscreteLevelData()` reads the already prepared `discreteLevels.dat` file. It reads the per-nuclide level count and then loads exactly that many records. It does not call `riplSetNmax()`, and it does not choose among RIPL `Nol/Nmax/Nc` at runtime.
2. **RIPL preparation utility:** under `DEVUTIL`, `riplReadDiscreteLevelData()` reads `RIPLDATA` (`ripl3-levels.dat`) and explicitly sets `MaxLevelCtl ml = reassign`. `riplSetNmax(ml, nol, nmax, nc)` therefore selects `Nmax` for this utility path. It then writes the selected level records to the prepared CGMF data format (the routine's output/write section is in the same source file).

This is a plausible and source-supported explanation for why the checked-in I-136 table has one level when RIPL-3 metadata gives `Nmax=1`. It is **not yet proof** that the current checked-in `data/discreteLevels.dat` was generated by this exact utility invocation/version. The exact generation event, command, input hash, output hash, and any post-processing remain unrecorded in the repository evidence examined here.

## Source facts

### A. Runtime loader does not perform RIPL Nmax/Nc selection

File: `libcgmf/src/ripl2levels.cpp`, function `readDiscreteLevelData()`.

- The function header explicitly describes the input as a CGMF-ready file processed for CGMF use, rather than the RIPL-3 database.
- It opens `DISCRETEDATA`, defined in `libcgmf/include/ripl2levels.h` as `discreteLevels.dat`.
- It reads the file's ZAID and level count, allocates that many `Level` objects, and loops over exactly that count.
- It loads energy, spin, parity, half-life, gamma count, final-state indices, branching probabilities, and internal-conversion coefficients.
- It does not call `riplSetNmax()`; the local `MaxLevelCtl ml` declaration/assignment in this loader is not used in the load loop.

Consequently, `ndisc=1` at runtime reflects the prepared file's declared level count (or a different file selected through the configured data path), not a runtime application of `Nc` or `Nmax`.

### B. The legacy DEVUTIL preparation path selects Nmax

File: `libcgmf/src/ripl2levels.cpp`, function `riplReadDiscreteLevelData()`, compiled under `#ifdef DEVUTIL`.

- It sets `ml=reassign`.
- It opens `RIPLDATA`; the header defines this as `ripl3-levels.dat`.
- It reads RIPL header fields `Nol`, `Nmax`, and `Nc`.
- It calls `riplSetNmax(ml, nol, nmax, nc)`.
- In `riplSetNmax()`, both `extended` and `reassign` select `nmax`; `normal` selects `nc`; `all` selects `nol`.
- The routine stores only records with index below the selected `nlevel`, while consuming the full RIPL isotope record so the next isotope remains correctly aligned.

The source also contains `riplFixNmax()`, which truncates at the first unassigned spin/parity, but that is called only for `extended` mode in the inspected code. It is not the selected `reassign` mode in this legacy utility.

### C. What the current I-136 comparison means

The prior Run #317 RIPL-vs-runtime audit recorded I-136 as:

- RIPL-3 `Nol=11`
- RIPL-3 `Nmax=1`
- RIPL-3 `Nc=1`
- CGMF runtime `ndisc=1`

This equality is consistent with the legacy utility's `reassign -> Nmax` selection. It does **not** establish an accidental runtime truncation, and it does not establish that all 11 RIPL levels should be loaded as experimentally complete low-lying levels.

The checked-in data directory includes both `ripl3-levels.dat` and `discreteLevels.dat`; the former is the named input expected by the legacy utility, and the latter is the runtime input. The repository's 2021 CGMF 1.1.0 data-change note says the `discreteLevels.dat` file was expanded to include all isotopes, but does not identify the exact generator command, mode, notebook revision, or source-file checksum.

## External documentation cross-check

The CGMF User Manual's discrete-level preparation page independently states that the CGMF-specific file is produced from RIPL-3 using `transformLevelDataFile.ipynb` and `Nucleus.py`, with steps to read the complete RIPL data, fix missing/unassigned spin and parity, and fix gamma transitions:

- https://cgmf.readthedocs.io/en/latest/discreteLevels.html

This documentation establishes the intended preparation concept, but it does not prove that the branch's checked-in files were generated from that particular notebook implementation. The branch contains no matching `transformLevelDataFile.ipynb` or `Nucleus.py` in the inspected repository paths. The legacy C++ DEVUTIL path is therefore an additional plausible preparation route, not something to silently equate with the Python notebook workflow.

## Consequences for the Run #317 hypothesis

The working hypothesis remains:

> A one-level I-136 discrete scheme places the continuum/discrete matching boundary at the ground state, allowing low-energy continuum bins (including the event-6 19.06-keV bin) to remain represented by the statistical continuum model. The observed high-spin continuum state is therefore not automatically an experimentally established 6− discrete level.

This remains **CANDIDATE**, not proven. The provenance audit strengthens the explanation for why the runtime table has one level, but does not itself demonstrate that the continuum-tail mechanism caused the bridge rejection.

The evaluated 201-keV I-136 (6−) level remains energetically inaccessible from the Run #317 event-6 state at 19.06 keV. It must not be inserted into the low-energy discrete scheme as a possible endpoint.
